### 9.3 Account-pool behaviour from code (step 7)
- **Locks.** Per account and queue (operation name, e.g. `SearchTimeline`) in `accounts.locks`. Acquire sets the queue lock to now+15 minutes and `last_used` (`accounts_pool.py:283-310`); release = `unlock` or `lock_until(reset)` after a rate limit (`queue_client.py:224-240`). Selectable = `active` and lock NULL or past (`:312-324`). A stale in-use lock (crash) expires by itself after 15 minutes.
- **Ordering.** `ORDER BY username LIMIT 1` (`:36-37,320`): the same first account while unlocked. `_order_by` can only be overridden as a process-global class attribute holding an SQL fragment (e.g. `"last_used ASC, rowid ASC"`; NULLs sort first; `last_used` is written in two text formats, ordering UNVERIFIED). Not recommended.
- **Codes** (`queue_client.py:307-332`): remaining 0 with reset above 0: lock the queue until reset, rotate; `(88) Rate limit exceeded` with remaining >0, `(326) Authorization: Denied by access control`, `(32) Could not authenticate you`, bare 403: `mark_inactive` (`active=false`, `error_msg`; None for bare 403). Other 4xx/5xx: 15-minute lock and rotate (`:356-361`). `LoadShed`/`DeadlineExceeded`: up to 3 retries on the same account with `sleep(2**n)` (`:82-93`). Transport errors: 3 retries, then a 60-second cool-down and rotate. Unknown exceptions: 3 attempts, then 15 minutes. Missing cookies: inactive.
- **Silent rotation.** After any of these the same `QueueClient.req` loop takes the next account and **continues the same cursor** (`:373-428`): one search can span two accounts with no event for the caller. No account left: `NoAccountError` if raising, else a silent end.
- **Pinning one unit to one account.** No parameter exists. `_get_and_lock(queue, username)` (`:283-285`) is private, skips the `active`/lock checks and interpolates the username into SQL. Recommended design A: **one SQLite file and one `API` per account** (as P-X9 already does): failover inside a unit is impossible, a ban/lock raises `NoAccountError`, and our code does LRU, the global budget and the restart. Design B: subclass `AccountsPool` and override `get_for_queue`. Find the cause of a `NoAccountError` from the row (`await pool.get(label)`: `active`, raw `error_msg`, `locks`, `last_used`, `stats`): inactive = ban/logout, active with a future lock = rate limit.
- **`reset_locks`** (`:255-257`) clears ALL locks, including valid rate-limit locks; there is no "older than 15 minutes" variant and none is needed (self-expiry). SPEC 18(k) should say: do not call it at start; keep our own UTC-day locks in our state (the library's rate-limit lock lasts only until the header reset, about 15 minutes).
- **Cookie upsert:** `await pool.add_account_cookies(label, cookies)` (does not clear locks or stats); `pool.reactivate([label])` re-enables an account that still has `auth_token` and `ct0`.
- **Unmetered traffic:** per process start and account, the transaction-id setup (x.com/tesla plus JavaScript bundles); each library retry (3 transport/loadshed, 3 XClId-404, httpx `retries=3`) is another request. Count PAGES fetched from `search_raw`, not parsed tweets.
