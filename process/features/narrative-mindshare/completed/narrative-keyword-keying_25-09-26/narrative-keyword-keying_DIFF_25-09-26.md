## Summary (written by vc-execute-agent after the run)

- **What changed:** in both scenarios, every seed category (ai, rwa, l2s, memecoins) goes from
  reading 1 source (coingecko only; pytrends/reddit empty) to reading all 3. Trust weight rises
  from 0.4 (the reduced-source cap, `n_available < 2`) to 0.6 (base weight). 8 of 8 category rows
  changed.
- **What did not change:** `triggered` (True in all rows, old and new), `confirmed` (False in all
  rows), per-source adapter status (all `ok` — this field is the adapter's own status and was never
  the bug), and every screener coin state (BTC `unavailable`, ETH `in-focus`, HYPE `in-focus`).
  The fix raises confidence; on this seed it does not flip any trigger or any badge.
- **Golden fixture, unchanged:** the contract test (`test_narrative_categories_contract.py`,
  3 tests) **passes against the unchanged golden fixture** with the new code + keyword-keyed seed.
  Reason: the golden file was captured with the old code reading a category_id-keyed seed, so the
  old read and old seed keys matched and all 3 sources were seen (trust 0.6). The new code reading
  a keyword-keyed seed gives the same result. The old code against the realistic keyword-keyed
  seed would NOT match the golden (it gives trust 0.4). In other words, the golden values already
  describe the corrected behaviour; step 8's fixture regeneration is expected to be a no-op
  (byte-identical), subject to user sign-off.
- **Real-world implication:** in production (no stubbed seed), the pre-fix code always read
  pytrends/reddit as empty, so every category ran on coingecko alone and was capped at 0.4 trust
  whenever it triggered. After the fix, categories with archived pytrends/reddit history can reach
  0.6 (unconfirmed) / 0.9 (confirmed).
